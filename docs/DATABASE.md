# Database Standard — General Core Kit

## Mandatory instruction for Antigravity and all coding agents

This document defines a **general-purpose database foundation** that any project can start from. It is **not tied to any one application**. Do not add tables, columns, names, or rules that only make sense for one business or product to the core kit. Project-specific structures belong in the project layer (Section 2).

Directly implement this standard in migrations, functions, policies, and tests. Do not stop at recommendations or diagrams when implementation is requested.

**STRICT: Every table, function, view, and policy must follow this standard. Do not skip a single applicable table or state.** Where a rule cannot be met, report it as **Blocked** with the reason instead of silently deviating.

Preserve existing data, business logic, permissions, and working behavior. Never edit an applied migration; add a new one. Never weaken security (`SECURITY.md`) to make a feature easier.

> SQL in this document is **reference code**. Test and adapt it before relying on it, and cover it with the tests in Section 17.

## 1. Principles

1. **General first.** The kit knows about organizations, units, people, access, money-like ledgers, schedules, and catalogs; it does not know about any specific industry.
2. **The database is the security boundary.** Rules live in constraints, RLS, and functions, not in the UI.
3. **Never lose history.** Master data is soft-deleted, documents are cancelled or voided, ledgers and logs are append-only.
4. **Every write can be retried safely** (idempotency).
5. **One way to do each thing.** Same columns, same helpers, same naming everywhere.
6. **Do not generalize speculatively.** A structure moves into the kit only when a second project needs it.
7. **Real columns beat flexible blobs.** Anything filtered, reported, or constrained gets a real typed column.

## 2. Layers

| Layer | Contents | Changes per project? |
| --- | --- | --- |
| **0. Conventions** | ULID keys, standard columns, soft delete, idempotency, audit, RLS pattern | Never |
| **1. Core tables** | Organizations, units, persons, profiles, roles/permissions, audit, idempotency, settings, counters, files, notifications, lookups | Rarely |
| **2. Optional modules** | Ledger, resources and reservations, catalog and pricing, inventory, workflow events | Install only what is needed |
| **3. Project layer** | Tables unique to one application, built using layers 0–2 | Always |

Dependencies point downward only: a lower layer never references a higher one.

## 3. Schema layout and naming

- `core` schema: helper functions, `idempotency_keys`, `audit_log`, `counters`, and other internal tables. **Not exposed through the API.**
- `public` schema (or a dedicated `api` schema): tables and views that clients may reach, **always with RLS**.
- Optional modules may use their own private schema (for example `ledger`) with exposure through RPCs or views.
- Names: `snake_case`, plural table names, singular column names, `_id` suffix for foreign keys, `_at` for timestamps, `_by` for actor references, `is_`/`has_` for booleans.
- Constraint and index names include the table and purpose (`<table>_<cols>_uq`, `<table>_<col>_chk`, `<table>_<cols>_idx`).
- Every foreign-key column and every column used in an RLS predicate is indexed.

## 4. ULID primary keys

- Every table's primary key is `id text` containing a ULID: 26 characters, Crockford base32, time-sortable.
- Declare with a format check and byte-order collation:

```sql
id text collate "C" primary key default core.ulid()
  constraint <table>_id_ulid_chk check (id ~ '^[0-7][0-9A-HJKMNP-TV-Z]{25}$')
```

- Foreign-key columns use the same type and collation.
- `id` is **immutable** (trigger rejects any change).
- IDs may be generated by the client (required for offline and idempotent creation) or by the database default. The server always validates the format.
- `auth.users.id` stays a UUID. It is referenced only from `profiles.auth_user_id`; nothing else references it.
- ULIDs reveal creation time. They are identifiers, **not** secrets and **not** authorization.
- Use keyset pagination (`where id < $cursor order by id desc limit $n`) instead of offsets.

Reference generator (48-bit millisecond timestamp + 80 random bits, Crockford base32):

```sql
create schema if not exists core;

create or replace function core.ulid() returns text
language plpgsql volatile set search_path = '' as $$
declare
  enc text := '0123456789ABCDEFGHJKMNPQRSTVWXYZ';
  ts  bigint := floor(extract(epoch from clock_timestamp()) * 1000)::bigint;
  rnd bytea := extensions.gen_random_bytes(10);
  res text := '';
  i int; b int; v int;
begin
  for i in 0..9 loop
    res := res || substr(enc, ((ts >> (5 * (9 - i))) & 31)::int + 1, 1);
  end loop;
  for i in 0..15 loop
    b := (i * 5) / 8;
    v := (get_byte(rnd, b) << 8) | get_byte(rnd, least(b + 1, 9));
    res := res || substr(enc, ((v >> (16 - ((i * 5) % 8) - 5)) & 31) + 1, 1);
  end loop;
  return res;
end $$;
```

The browser uses a small dependency-free equivalent built on `crypto.getRandomValues`. Both generators must pass the same format test.

## 5. Standard columns and helpers

Every business table has these columns (omit only with a documented reason):

| Column | Purpose |
| --- | --- |
| `id` | ULID primary key |
| `org_id` | Tenant owner, `not null`, references `orgs` |
| `unit_id` | Branch/site/campus/venue scope, nullable, references `org_units` |
| `created_at`, `created_by` | Server-stamped; never accepted from the client |
| `updated_at`, `updated_by` | Server-stamped on every update |
| `version` | Integer starting at 1, incremented on every update, for optimistic concurrency |
| `deleted_at`, `deleted_by`, `delete_reason` | Soft delete, **master-data tables only** |
| `meta` | `jsonb not null default '{}'`: small, non-critical extras only; never used for filtering, reporting, or rules |

Reusable helpers (installed once in `core`):

- `core.attach_standard(table regclass)`: attaches triggers that (a) reject `id` changes, (b) stamp `created_*`/`updated_*`/`version`, (c) reject direct hard deletes, (d) write the audit log.
- `core.enable_standard_rls(table regclass, scope text)`: enables RLS and creates the standard policies for scope `org`, `unit`, or `own`, using permission codes (Section 8).
- `core.current_profile_id()`: returns the active profile for the caller (`stable security definer`, `search_path = ''`).
- `core.has_permission(org_id text, unit_id text, code text)`: the single authorization check used by policies and RPCs.

Creating a new table in any project is: create the table with the standard columns, call `attach_standard`, call `enable_standard_rls`, then add only what is project-specific.

Rules:
- Clients cannot write `created_*`, `updated_*`, `version`, `deleted_*`, `org_id` (after creation), or any status field protected by workflow. Use column-level grants, triggers, or RPCs.
- `org_id` and `unit_id` cannot be changed after creation unless an explicit, permissioned, audited "move" RPC exists.
- Updates from the client send the expected `version`; a mismatch returns a conflict instead of overwriting.

## 6. Removal model: soft delete, void, append-only

Every table is classified in its migration comment as exactly one of:

| Class | Typical content | Mechanism |
| --- | --- | --- |
| **Master data** | Things that are set up and reused (people, items, resources, plans, units) | **Soft delete**: `deleted_at`, `deleted_by`, `delete_reason` |
| **Document** | Things that happen at a point in time and have a lifecycle | **Cancel / void / withdraw** with status, reason, actor, and time. Never deleted. Corrections create reversing entries, not edits |
| **Ledger / log** | Entries that record facts | **Append-only**. No updates, no deletes. Corrections are new reversing rows |

### Soft delete rules
- `deleted_at is null` means active. `deleted_at`/`deleted_by` must be both set or both null (`CHECK`).
- Clients never write `deleted_*` directly. Use RPCs `soft_delete_<entity>(id, reason, idempotency_key)` and `restore_<entity>(id, idempotency_key)`.
- Both actions check permission, check business guards, stamp from the server, and write an audit entry.
- **Idempotent:** deleting an already-deleted row, or restoring an active row, returns success without overwriting the original `deleted_at`/`deleted_by`.
- **Business guards:** deletion is refused while the record is still in use (open documents, non-zero balances, active children, future reservations). Each entity documents its guards.
- Restore is refused when it would violate a unique rule (see below), with a clear conflict message.
- A deleted row cannot be updated, except by restore.
- Uniqueness ignores deleted rows via **partial unique indexes**:

```sql
create unique index <table>_code_active_uq
  on public.<table> (org_id, code) where deleted_at is null;
```

- Add partial indexes for active-only lists: `... where deleted_at is null`.
- Lists and pickers read `*_active` views defined with `security_invoker = true`. Historical screens may still read deleted rows so old documents stay readable; documents also keep **snapshots** (names, prices) of what they referenced.
- No cascading deletes anywhere. Foreign keys are `on delete restrict`.
- Hard delete is blocked for client roles (`REVOKE DELETE`) and by a `BEFORE DELETE` trigger that allows only the dedicated maintenance role used by the retention job (Section 15).

### Void/cancel rules
- Status and `voided_at/by/reason` (or `cancelled_*`) are set only through RPCs.
- A void creates reversing ledger/stock entries in the same transaction and cannot happen twice.
- Voided/cancelled documents remain visible, clearly labelled with text (not color alone), and are excluded from totals by one consistent rule.

## 7. Idempotency

Every operation that changes data must be safe to retry. Three layers apply together.

### Layer 1: the document's ULID is its idempotency key
- For anything a user creates, the client generates the ULID when the form opens, stores it with the queued payload (including offline), and **reuses it on every retry**.
- The write is `insert ... on conflict (id) do nothing`, then the existing row is returned.
- Each document stores a `payload_hash`. The same ID with a **different** payload is rejected (`409 conflict`), because it is a bug or tampering.
- Validate ULID format server-side. Reject timestamps unreasonably far in the future. Allow past timestamps (offline queues can be days old).

### Layer 2: `idempotency_keys` for all other operations
For actions that are not "create a document" (cancel, void, delete, restore, check-in, approve, record entry, state changes, calls to Edge Functions):

```sql
create table core.idempotency_keys (
  id            text collate "C" primary key,           -- key sent by the client (ULID)
  org_id        text not null,
  actor_id      text not null,
  scope         text not null,                           -- operation name
  request_hash  text not null,                           -- hash of the normalized payload
  status        text not null check (status in ('in_progress','completed','failed')),
  response      jsonb,
  created_at    timestamptz not null default now(),
  completed_at  timestamptz,
  expires_at    timestamptz not null default now() + interval '30 days',
  unique (actor_id, scope, id)
);
```

Behavior inside the RPC, in one transaction:
1. Insert the key as `in_progress` with `on conflict do nothing`.
2. If it already existed: same hash and `completed` → **return the stored response**; `in_progress` → return `409 retry later`; different hash → `422 key reused with a different request`.
3. Perform the work, store the response, mark `completed`.
4. A scheduled job removes expired rows. Clients cannot read this table.

Edge Functions accept an `Idempotency-Key` header and use the same table.

### Layer 3: natural uniqueness as the last line of defense
- Child rows: unique on `(parent_id, line_no)`.
- Ledger entries: unique on `(source_type, source_id, client_ref)`.
- Membership/assignment tables: unique on the pair they link.
- Human-readable numbers: unique on `(org_id, unit_id, series, number)`.
- Single-result rules: partial unique index (for example one final result per record).

### Client rules
Generate the key on the first attempt. Reuse it for every retry, reload, and offline replay. Discard it only after a definitive result. A new user intent gets a new key.

## 8. Tenancy, permissions, and RLS

- **Multi-tenant by default.** Every business table has `org_id`. A single-business project simply has one organization.
- `org_units` model branches, sites, campuses, or venues; they may have a parent for hierarchies.
- Authorization is based on **permission codes** (`<module>.<action>`, such as `records.read`, `ledger.void`), never on hardcoded role names. Roles are bundles of permissions defined by seed data per project.
- `org_members` links a profile to an organization (and optionally a unit) with a role. It is the table RLS reads.
- Every client-reachable table, view, and storage bucket has RLS enabled with explicit per-operation policies. No `using (true)` except documented public read-only data.
- Standard policy shape:

```sql
create policy <t>_select on public.<t> for select to authenticated
  using (core.has_permission(org_id, unit_id, '<module>.read'));
create policy <t>_insert on public.<t> for insert to authenticated
  with check (core.has_permission(org_id, unit_id, '<module>.create'));
```

- Scope `own` additionally requires the row to belong to the caller's person/profile.
- Wrap `auth.uid()` as `(select auth.uid())` inside helpers for performance.
- `security definer` functions: `set search_path = ''`, fully qualified names, validate the caller inside, and revoke `EXECUTE` from `public` and `anon` unless intended.
- Views use `security_invoker = true`.
- Users cannot change their own role, unit, org, or active status. Inactive or removed users lose access immediately (`is_active` and `deleted_at` are checked by `has_permission`).
- Writes to money-like, stateful, or multi-table data go **only through RPCs**; direct `INSERT/UPDATE/DELETE` is revoked from `anon` and `authenticated`.
- Public-facing read access (for example availability) is provided by narrow views that expose only the minimum columns.
- Revoke default privileges from `anon`/`authenticated` on new objects, then grant explicitly.

## 9. Core tables (always installed)

Each also carries the standard columns of Section 5 unless noted.

| Table | Purpose | Class |
| --- | --- | --- |
| `orgs` | Top-level tenant | Master |
| `org_units` | Branch/site/campus/venue, optional `parent_id` | Master |
| `persons` | Anyone the system records: `kind`, names, contact fields, optional date of birth, optional `profile_id`. A person does not need a login | Master |
| `person_relations` | Guardian, emergency contact, family links, with relation type | Master |
| `profiles` | Login identity: `auth_user_id uuid unique references auth.users`, `is_active`, optional `person_id` | Master (deactivate, never hard delete) |
| `roles`, `permissions`, `role_permissions` | Permission catalog and role bundles | Master |
| `org_members` | Profile ↔ org (↔ unit) ↔ role, `is_active` | Master |
| `settings` | Scoped key/value (`org` or `unit`), jsonb value, validated; holds timezone, policies, limits | Master |
| `lookups` | Admin-editable lists: `type`, `code`, `label`, `sort`, `is_active` | Master |
| `counters` | Per org/unit/series number sequence, incremented under row lock | Internal |
| `files` | Metadata for stored objects: owner record, kind, size, checksum, uploader | Master |
| `notifications` | Outbound message queue and history: channel, recipient, template, status | Log |
| `tags`, `taggings` | Optional light classification | Master |
| `audit_log` | Insert-only record of changes and sensitive actions | Log |
| `idempotency_keys` | Section 7 | Internal |

Notes:
- Use `CHECK` constraints for fixed state sets and `lookups` only for lists administrators may edit.
- `persons` holds data about people who may be minors or otherwise sensitive; see Section 15.
- `meta` on any table is never a substitute for a real column.

## 10. Optional modules

Each module is a separate, versioned set of migrations that depends only on the core. Install only what the project needs. Each module defines its permission codes, tables, RPCs, and tests.

### 10.1 Ledger
Records any quantity that is added and subtracted over time: money, prepaid credit, points, stock quantities.
- `ledger_accounts`: owner (type + ID), `kind` (`money`, `credit`, `points`, `quantity`), unit of measure or currency, `is_active`.
- `ledger_entries` (**append-only**): `account_id`, signed `amount numeric(18,4)`, `source_type`, `source_id`, `client_ref`, `reverses_entry_id`, `occurred_at`, `recorded_by`, `note`.
- Unique on `(source_type, source_id, client_ref)`. A reversal references the entry it reverses and can reverse it only once.
- Balance = sum of entries. A cached balance table may exist, updated in the same transaction, and a scheduled reconciliation compares it with the sum.
- Constraints stop overdrafts where the account kind requires it (atomic conditional update, never read-then-write).
- Corrections are reversing entries, never edits.

### 10.2 Resources and reservations
Anything that can be reserved for a time range: rooms, equipment, vehicles, staff, spaces.
- `resources` (master): type, name, capacity, `is_active`.
- `reservations` (document): `resource_id`, `during tstzrange`, `status`, `payload_hash`, cancel columns.
- `blackouts` (master): unavailable ranges. `holds` (log): temporary holds with `expires_at`.
- Prevent overlaps in the database:

```sql
create extension if not exists btree_gist with schema extensions;

alter table public.reservations add constraint reservations_no_overlap
  exclude using gist (resource_id with =, during with &&)
  where (status in ('pending','confirmed','checked_in'));
```

- Use half-open ranges `[start, end)` so back-to-back reservations do not conflict.
- Also check blackouts, operating hours, and minimum/maximum duration inside the create RPC.
- Expired holds are released by the RPC or a scheduled job. A friendly "slot taken" result is returned on conflict.

### 10.3 Catalog and pricing
Things that can be offered, priced, and referenced: products, services, plans, fees.
- `items` (master): kind, code, name, `is_active`.
- `price_rules` (master, **effective-dated**): item, validity range, optional day/time band, amount. Never edit a price; add a new effective row.
- Documents copy a **snapshot** of name and price at the time (`name_snapshot`, `price_snapshot`, `price_rule_id`).

### 10.4 Inventory
Built on the ledger with `kind = 'quantity'`.
- `stock_levels` (cache per item and unit) updated in the same transaction as the ledger entry.
- Deduct with `update ... set qty = qty - $n where qty >= $n` and check the row count, so concurrent requests cannot oversell.
- Transfers between units are one transaction with two entries.

### 10.5 Workflow events
- `entity_events` (**append-only**): entity type and ID, from/to state, actor, reason, timestamp. Use for any lifecycle you want to audit or replay.

## 11. Document pattern (a convention, not a shared table)

Every transactional document table (anything with a lifecycle) includes:

`id` (ULID, first idempotency layer), `doc_no`, `status` (with `CHECK` and a documented state machine), `payload_hash`, `version`, and `voided_at/by/reason` (or cancelled/withdrawn equivalents), plus a snapshot of any referenced master data (names, prices, rates).

- Child lines: `(parent_id, line_no)` unique; never updated independently of the parent's state rules.
- Do **not** create one giant polymorphic "documents" table; it loses foreign-key integrity.
- Status transitions happen only in RPCs that validate the allowed transition and record an `entity_events` or audit row.
- Derived values (paid status, balances, totals) come from ledger and line data, never typed in by hand.

## 12. Time, money, and numbering

- All instants are `timestamptz`. The business timezone is a setting (default `Asia/Manila`); display and "business date" calculations convert with `at time zone`.
- Money and quantities use `numeric` with explicit precision, never `float`. Currency/unit of measure is stored with the amount or account.
- Amounts and quantities have `CHECK` constraints for valid ranges.
- Human-readable numbers (`doc_no`) come from `counters` under row lock, formatted per series (prefix, year, zero-padded). Promise uniqueness, not gapless sequences. Offline creation may carry a local reference that is replaced by the real number on sync (store both).
- The ULID remains the real identity; numbers are for people.

## 13. Integrity and concurrency

- `NOT NULL`, `CHECK`, `UNIQUE`, and foreign keys encode every rule that can be encoded.
- Multi-table writes run in **one transaction** inside an RPC.
- Use atomic conditional updates, `SELECT ... FOR UPDATE`, exclusion constraints, or unique indexes for contention; never read-then-write in application code.
- Optimistic concurrency uses `version`.
- Set `statement_timeout` for client roles; enforce maximum page sizes; index filtered and joined columns.
- Never trust client-supplied totals, prices, ownership, status, or timestamps; recompute or stamp on the server.

## 14. Audit and logging

- `audit_log` is insert-only for everyone, including administrators. It records actor, action, table, record ID, old and new values, request ID, and time.
- Audited at minimum: sign-ins and failures, role/permission/membership changes, soft deletes and restores, voids and cancellations, ledger reversals, price/rule changes, data exports, account creation and deactivation, and configuration changes.
- Never log passwords, tokens, or full personal identifiers; mask personal data.
- `core.attach_standard` wires the audit trigger by default.

## 15. Privacy, retention, and purge

- Personal data is governed by the Philippine Data Privacy Act (RA 10173) unless the project states otherwise. Collect only what is needed and record the purpose.
- Restrict personal fields to roles that need them; expose minimal fields in shared views.
- Treat minors and sensitive categories with extra care: guardian links, consent records (append-only), and limited visibility.
- Define retention per table. Financial and audit records follow the legal retention period (confirm with an accountant or counsel).
- When a person must be erased but history must remain, **anonymize** (replace identifying fields with a redaction marker, keep the ULID) instead of deleting.
- A scheduled purge, run only by the dedicated maintenance role, hard-deletes soft-deleted rows that are past retention **and** unreferenced, and writes the purge to the audit log.
- Never place real personal data in the repository, seeds, screenshots, or documentation.

## 16. Migrations, versioning, and packaging

- One migration per change, with a timestamped, descriptive name. **Never edit an applied migration.**
- Kit migrations use numbered names (`0001_core_*.sql`, `0100_module_ledger_*.sql`); project migrations start at `1000`.
- The kit lives in its own **template repository** (for example `db-core`) with a `CHANGELOG.md` and semantic versions (`core v1.0.0`). Each project records the kit version it started from and applies upgrades as new migrations.
- The repository is public: it contains structure, functions, tests, and **fake** seed data only.
- Seeds (permissions, default roles, lookups) are idempotent (`on conflict do nothing`).
- Apply migrations to a development project first, then production. Take a backup before risky migrations and keep a rollback plan.
- Run Supabase Security and Performance Advisors after every migration and resolve all findings.
- Every migration comments each new table with its **class** (master, document, ledger/log, internal) and its permission codes.

## 17. Testing (portable pgTAP suite shipped with the kit)

- [ ] `core.ulid()` output matches the format check; the client generator produces valid values; sort order follows time.
- [ ] `id`, `org_id`, `created_*` cannot be changed by clients.
- [ ] Hard delete is blocked for client roles and by trigger.
- [ ] Soft delete: stamps correct actor/time; second call is idempotent and does not overwrite; restore works; restore conflicts on duplicate unique keys; deleted rows reject updates; business guards refuse deletion of in-use records.
- [ ] Partial unique indexes allow reuse of a code after soft delete.
- [ ] Idempotency: same key and payload returns the stored response; same key and different payload is rejected; concurrent duplicate returns `in_progress`; expired keys are cleaned.
- [ ] Document create: same ULID retried returns the same row; same ULID with a different payload is rejected.
- [ ] RLS: a user in org A cannot read or write org B even with a guessed ULID; unit scoping works; inactive users lose access; users cannot change their own role or unit.
- [ ] Permission checks use codes; removing a permission removes access.
- [ ] Ledger: entries cannot be updated or deleted; a reversal works once; overdraft rules hold under concurrency; cached balance equals the sum.
- [ ] Reservations: simultaneous requests for the same resource and time produce exactly one success; back-to-back ranges both succeed; cancelled reservations free the range; blackouts block.
- [ ] Optimistic concurrency: stale `version` is rejected.
- [ ] Audit log is insert-only and captures the actions in Section 14.
- [ ] Anonymous role cannot read or write any table, view, or RPC unless explicitly intended.

## 18. Starting a new project from the kit

1. Create the project from the kit template; confirm the kit version.
2. Create the Supabase projects (development and production) with separate keys.
3. Apply core migrations; run the portable test suite.
4. Install only the optional modules the project needs.
5. Seed the project's permissions, roles, settings, and lookups (fake data in the public repo).
6. Add project tables: standard columns, `attach_standard`, `enable_standard_rls`, class comment, partial unique indexes, snapshots, document pattern for lifecycle tables.
7. Write RPCs for every state change, with idempotency, permission checks, guards, and audit.
8. Add project-specific tests alongside the portable suite.
9. Record the project's permission matrix, table classification list, and retention rules.
10. Update `TECH_STACK.md` and `SECURITY.md` if anything differs.

## 19. Strict implementation and acceptance checklist

Before editing, inventory every table, view, function, policy, trigger, index, bucket, and scheduled job. Include hidden, internal, and dynamically created ones.

Maintain a coverage checklist with each item marked **Updated**, **Verified**, or **Blocked**. A blocked or unverified item is not complete.

- [ ] Every table has a ULID `id`, the standard columns, and a documented class.
- [ ] `core.attach_standard` and `core.enable_standard_rls` applied to every business table.
- [ ] RLS enabled with explicit per-operation, permission-code policies; defaults revoked for `anon`/`authenticated`.
- [ ] Multi-tenant isolation (`org_id`) proven by tests.
- [ ] Hard deletes blocked; soft delete and restore implemented through idempotent RPCs with business guards.
- [ ] Partial unique and partial active indexes in place for every soft-deletable table.
- [ ] Documents have status machines, void/cancel columns, snapshots, `payload_hash`, and reversing-entry logic.
- [ ] Ledgers and logs are append-only and enforced by privileges and triggers.
- [ ] All three idempotency layers implemented where applicable; retries tested.
- [ ] Contention-prone operations use exclusion constraints, unique indexes, atomic updates, or row locks.
- [ ] Money and quantities use `numeric`; times use `timestamptz`; business timezone setting respected.
- [ ] Audit log captures all required events and is insert-only.
- [ ] `security definer` functions hardened; views use `security_invoker`.
- [ ] Privacy classifications, retention periods, and anonymization/purge procedures documented.
- [ ] Migrations are new files only, versioned with the kit, and advisors show no unresolved findings.
- [ ] Portable and project tests pass.
- [ ] Nothing project-specific has leaked into the core kit.

**Completion rule:** Do not claim the database is complete based on a successful migration run, one verified table, or passing syntax checks. Report the migrations and files changed, the tables and functions covered, the verification performed, and every remaining blocker. No skipped item is acceptable under a claim of completion.
